Abstract

Can a handful of search-performance signals flag which content pages are worth reviewing before they quietly lose traffic?

This paper asks whether pages showing early signs of search decline can be identified early enough to act on, using only signals a team would actually have on hand at decision time. Working from FlyRank's anonymized search-performance warehouse, I built a scoring pipeline that ranks pages by refresh urgency, starting from a hand-written rule baseline and testing whether a simple learned model could beat it under an honest, client-grouped validation split.

Under a client-grouped, time-aware validation split, a hand-written rule baseline reached a Precision@50 of 0.56. An initial logistic regression model appeared to reach 0.94 — until an audit revealed the label definition had arithmetically embedded one of the model's own input features, producing an inflated, unreliable score. After removing that feature and rebuilding the label independently, the corrected model reached a genuine Precision@50 of 0.84, a real improvement over the baseline. The result is a ranked, human-reviewed content action queue — not a fully automated system — intended as a monthly prioritization aid for content teams, together with the honest account of the leakage that nearly went unnoticed.

Introduction

Content teams managing large page libraries face a recurring, unglamorous problem: which pages, out of thousands, actually need attention this month? Manually reviewing every page doesn't scale, and naive heuristics — "anything older than six months" — miss the interaction between staleness, visibility, and search performance that actually predicts decline.

The decision this work supports: a content editor or SEO strategist choosing which pages to prioritize for refresh each cycle, working from a ranked shortlist instead of guessing.

Why this matters practically: the cost of getting this wrong is asymmetric. A false positive (flagging a healthy page) wastes an afternoon of editorial time. A false negative (missing a genuinely declining page) can mean weeks of silently eroding organic traffic before anyone notices — which is the more expensive failure mode, and the one this work is tuned to avoid.

This work started from a real, recurring problem inside FlyRank's own content operations: content teams managing large page libraries can't manually review every page each month, and naive heuristics ("anything older than six months") miss the interaction between staleness, visibility, and search performance that actually predicts decline. This paper is that problem, worked end-to-end — from framing a measurable question, through a real production-scale warehouse, to a ranked action queue a content team could actually use, and including an honest account of a leakage mistake caught and fixed along the way.

Time window

Features are built from month=2026-03 (a mid-panel month), with outcomes measured against 2026-04 to build a genuine past→future label. June 2026 — the final month in this release — was deliberately excluded from all development and treated as a sealed test month, since it is the natural outcome window for any past→future label built anywhere in this release.

What I excluded, and why

  • All client and content identifiers from any public output — this paper reports only aggregate patterns.
  • AI-referral columns (ai_chatgpt, ai_perplexity, etc.) — out of scope for this lane; mixing them in would blur what this analysis specifically tests (search/refresh signals).
  • The June 2026 _sample table for anything beyond query-mechanics testing — using it to develop label logic would leak the natural outcome window into development.

Methodology

Task framing

This is a scoring task built on a binary classification proxy. The deliverable an editor acts on is a ranked list, not a single yes/no prediction.

Label / proxy

is_declining: 1 if a page's April click volume falls meaningfully below its March daily rate (more than a 15% drop, annualized), 0 otherwise. This is a proxy, not a ground-truth "needs refresh" signal — a page can decline for reasons a refresh won't fix, which is addressed directly in Limitations.

Features (all knowable at decision time)

FeatureAvailable because…
Average impressionsBuilt only from March data, before the decision point
Average clicksHistorical, not future
Average search positionKnown as soon as the month's crawl data lands
Click-through rateComputed from already-observed clicks/impressions

Baseline

A hand-written rule: score = staleness × visibility × impression volume, using fixed thresholds (180+ days since update, 500+ impressions).

Validation design

Client-grouped, time-aware split. Pages are grouped by client so that no client's pages appear in both train and test — a naive row-level split would leak client-specific patterns and overstate performance, which I confirmed directly (see Results).

Leakage checks

All four features are confirmed to derive only from the March window; the April-derived label is used exclusively as the outcome, never as an input. Feature-label correlations were checked for any suspiciously high value that might indicate an accidental near-duplicate of the label.

Results

Model vs. baseline (same split, same metric)

MethodPrecision@50
Hand-written baseline rule0.560
Logistic Regression — original features (later found leaky)0.940
Logistic Regression — corrected features (honest)0.840
A leakage finding, reported honestly: the original 0.940 score used avg_clicks as both a model feature and part of the label's threshold definition — a mechanical, formulaic link, not genuine predictive skill. Random Forest under this original setup reached a suspicious Precision@50 of 1.000 with zero false positives in its top 50, which was the signal that prompted the audit. After removing avg_clicks from the feature set and rebuilding the label independently from any single feature, the corrected model reached 0.840 — still a real, meaningful improvement over the 0.560 baseline, and one I trust.

What the errors look like

Feature correlations with the corrected label are modest and reasonable (avg_impressions: 0.169, avg_position: −0.183, ctr: 0.180) — none near 1.0, unlike the leaky setup. The corrected model still misses roughly 16% of its top-50 calls, consistent with a genuinely hard, noisy prediction problem rather than an artificially easy one.

Ranked action distribution

Of 23,235 scored pages in the test split, 13,737 were labeled monitor (no urgent action), 5,356 review ranking strategy (position below page two), and 4,142 priority refresh (high decline risk with decent visibility) — the shortlist a content team would actually act on first.

Limitations & Honest Framing

This is a pattern study, not proof of cause and effect. All claims below use observed / directional / decision-support language deliberately.
  • Unbalanced panel: per-client history depth differs across this warehouse release; any pattern found could be skewed toward clients with longer, more complete history.
  • Proxy label, not ground truth: "declining" is a click-drop threshold, not a confirmed need for editorial refresh — a page can decline for reasons a content refresh won't address (seasonality, a competitor outranking it, an algorithm update).
  • Single time window: validated on one March→April transition; performance has not been confirmed to hold across multiple months or seasons.
  • Correlational, not causal: observed associations between signals (e.g., low CTR) and decline are not evidence that fixing the signal causes recovery.
  • No individual-page guarantees: this is a decision-support ranking tool for prioritization, not a prediction anyone should treat as certain for any single page.

Ranked Recommendations

The action playbook this analysis supports, in priority order:

01

Priority refresh — high decline risk, decent position & volume

The strongest, most defensible action: pages with real visibility that are showing genuine decline signals, not just age.

02

Fix CTR / snippet review — high impressions, low click-through

Cheap, fast fix for pages that are visible but under-converting that visibility into clicks.

03

Review ranking strategy — poor position (20+)

Likely needs more than a content refresh; flagged for human strategic review rather than automatic action.

04

Monitor — everything else

Not urgent. Revisit at the next monthly cycle rather than acting now.

Human review is required throughout

This tool ranks and flags; it does not publish, rewrite, or remove content automatically. Client-facing reporting should never present raw model scores directly — they are internal prioritization signals, not something to show a client as a percentage guarantee.
